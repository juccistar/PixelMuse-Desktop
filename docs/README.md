# PixelMuse 维护文档

本文档面向首次接手项目的开发者和维护者。用户启动与操作说明见[应用 README](../README.md)，工作区约束见[AGENTS](../AGENTS.md)。

## 三份项目基线文档

开发、升级或交接时先按顺序阅读这三份文档：

| 顺序 | 文档 | 回答的问题 | 更新时机 |
| --- | --- | --- | --- |
| 1 | [需求文档：项目目标与交付标准](requirements.md) | 产品解决什么问题，包含哪些业务，做到什么程度可以交付？ | 目标、范围、业务规则或验收标准变化时 |
| 2 | [项目技术栈文档](technical-stack.md) | 使用什么技术，各层如何协作，修改和升级会影响什么？ | 架构、依赖、数据结构、构建或发布机制变化时 |
| 3 | [项目当前进度文档](project-status.md) | 当前交付了什么，验证到哪里，有哪些限制，下一步建议做什么？ | 完成功能、执行验证、发布版本或确认限制时 |

需求中的交付标准与进度中的实际达成情况分别维护；下一步建议不自动视为已承诺需求。进度以日期和证据说明状态，不用未经度量的完成百分比。技术栈以代码与锁文件核对，版本、测试数及发布状态统一从当前进度和验证记录追溯。

## 文档与代码的关系

- `packages/contracts` 的 TypeBox schema 是通信契约的手写真相源；文档不是第二套 API 定义。
- 查询结果是业务状态真相，变更事件只负责通知重新查询。
- 来源记录、人工参考、模型建议和已核实商品事实必须分别表述。
- `archive/` 保存历史过程，不能据其中的旧待办恢复已移除的运行架构，也不能把历史验收套用到修改后的源码。
- 文件夹路径、命令和能力以当前代码为准；修改实现时同步更新相关维护页和实际验证记录。
